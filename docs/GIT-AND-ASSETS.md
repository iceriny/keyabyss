# Git、素材与跨设备协作方案

本方案适用于键渊当前的 Godot 开发。它规定推荐组织方式、工具职责和迁移顺序，不表示仓库、LFS 或同步工具已经配置完成。实际状态见[阶段总结](STAGE-SUMMARY.md)，实施待办只维护在 [TODO](TODO.md)。

## 1. 当前事实与推荐方向

2026-09-30 核查：

- `iceriny/keyabyss` 是公开仓库，默认分支为 `main`；当前 Godot 工作在 `codex/combat-system-deepening`，已经推送，尚未合入默认分支。
- 本机已安装 Git LFS 3.7.1，但根 `.gitattributes` 仅规定文本换行与二进制类型，没有启用 LFS 跟踪。
- 活动资源目录约为：插画与图形 9.49 MiB、音频 31.99 MiB、字体 55.02 MiB、词库 2.14 MiB，包含少量导入设置。
- 144 个音频原件约 1.35 GiB，仍在被忽略的旧素材目录中。游戏实际使用的是裁剪后的短音效，不能将两者视为无意义的重复文件。
- 一部分游戏音效和字体已经进入公开 Git 历史。其来源与尚缺的许可资料见[第三方声明](../THIRD_PARTY_NOTICES.md)。不能因为文件已有提交，就认定它适合继续公开分发。

已确定采用 **公开代码仓库＋私有资产仓库**：代码、场景、规则、文档和可公开的小资源留在主仓库；商业素材原件以及尚未确认可公开的资源，放在私有资产仓库，用 Git LFS 管理。大型视频原片若以后明显超过 LFS 使用预算，再放到独立存储，当前不建设第三套平台。

代码仓库保留公开，资产仓库独立授权。本轮确定方案，不创建仓库或迁移文件。

## 2. 哪些东西进入哪里

| 内容 | 推荐位置与方式 | 原因 |
| --- | --- | --- |
| GDScript、shader、场景、Resource、JSON、SVG、文档 | 主仓库，普通 Git | 适合审阅差异，与代码一起回退 |
| `.gd.uid` 等 UID 文件、资源旁的 `.import` 设置 | 主仓库，普通 Git | 属于项目引用和导入设置；不是 `.godot` 缓存 |
| 自有或允许公开的小型 PNG、短音效 | 主仓库，普通 Git | 当前规模不需要全部改用 LFS |
| 可公开但较大、经常变动的二进制资源 | 主仓库，按明确目录或文件启用 LFS | 让普通 Git 历史保持轻量；不只凭扩展名把全部小图迁走 |
| 商业音频原件、未确认可公开的字体／音效、美术源文件 | 私有资产仓库；二进制走 LFS | 有版本、可跨设备同步，访问范围独立于公开代码 |
| 从原件制作出的游戏版本 | 允许公开的留主仓库，否则在私有资产仓库的 `runtime/` | 保证换设备可以直接运行，不必先处理整套原件 |
| `.godot/`、预览、日志、转换中间文件、`.delete/` | 本机忽略 | 可再生成或属于工作记录，不是交付输入 |
| 引擎、第三方工具安装、凭据和机器路径 | 工具版本入 Git；程序与本地配置不入库 | 各设备按锁定版本安装，配置模板不含个人路径或令牌 |
| 发布 EXE／PCK／ZIP | 经发行检查后的 Release 附件 | 不随每次代码修改写进 Git 历史 |
| 大量视频原片、长时录屏 | 必要时使用私有文件／对象存储，Git 保存清单 | 不让频繁的大文件修改拖累日常拉取 |

主仓库的 `assets/` 仍是 Godot 的实际读取路径。哪些文件来自私有资产仓库由清单明确指定；不需要为了拆仓库改变游戏中的全部资源路径。

公开克隆没有私有素材时，准备工具应准确列出缺少的资源和取得方式，不能静默换上占位资源再声称完整游戏可运行。可选的公开演示素材是另一项内容工作，不作为本方案的前提。

## 3. “只保留一份”的具体含义

每份资产只有一个可维护的来源、一个负责它的仓库。相同字节可以用 SHA-256 找出重复；同名、听起来相似或看起来相似不能直接判重。

- 两个目录里完全相同的法书插画、字体或词库，确定活动版本后只维护活动版本。旧工程需要时由准备工具恢复到旧路径。
- 音频原件、剪出的游戏音效，以及美术源文件、导出的 PNG，是不同用途的文件。保留它们的来源关系，不能只留成品而丢掉以后编辑所需的原件。
- 同一声效有多个事件别名时，先让引用指向同一实际资源；不要为了不同文件名复制相同 WAV。保持不同音色或加工参数的变体。
- 缓存、同步副本和导出文件不再提交到另一仓库。为了运行而产生的本地副本可以存在，但不能在两处分别编辑、分别发布。

目标是只有一份权威来源和一次云端管理，不是承诺每台设备磁盘上永远只有一份字节。为避免 Windows 硬链接／符号链接造成编辑串改和权限差异，首版同步工具使用普通复制及校验。

## 4. 推荐目录与版本清单

以下为待实施的目标结构；私有仓库名称暂用 `keyabyss-assets`，并未创建。

```text
Workspace/
  keyabyss/                       # 游戏代码仓库
    assets/                       # Godot 实际使用的资源
    tools/assets/                 # 检查、同步及制作工具
    asset-lock.json               # 本次代码所需的精确资产版本
    docs/
  keyabyss-assets/                # 独立克隆，不嵌套进游戏仓库
    source/audio/                # 音频原件
    source/art/                  # 可编辑插画、模型等源文件
    runtime/audio/               # 游戏采用的加工结果
    runtime/fonts/
    recipes/                     # 选段、裁剪、导出参数
    catalog.json                 # 文件身份、哈希、来源与用途
    licenses/                    # 与素材访问范围一致的资料
```

主仓库 `asset-lock.json` 至少保存：schema 版本、资产仓库地址、完整提交 SHA，以及需要的资源条目。每条包含稳定资产 ID、资产仓库内路径、游戏目标路径、字节数和 SHA-256；原件额外记录制作依赖，但日常运行不必下载。

清单固定提交，不能写成“跟随素材仓库 main 最新版”。代码回到旧提交时，也能确定当时需要哪个素材版本。只在完整同步成功后记录本机同步状态；本机路径和认证信息不写进清单。体积很大的条目清单可以放在资产仓库，主仓库固定其提交和清单哈希，不为此重复维护两份可编辑记录。

资产仓库按二进制类型使用 LFS；目录里的 JSON、SVG、说明和制作参数仍用普通 Git。例如 WAV、FLAC、TTF、OTF、PSD、BLEND、MP4 的属性使用 `filter=lfs diff=lfs merge=lfs -text`。源文件需要排他编辑时可以加 `lockable`，但文件锁的服务端支持和客户端检查必须实测，不能只写一个属性就当作不会冲突。

素材仓库提交 SHA 只能在该提交和所需 LFS 对象已上传后进入代码清单。Git 提交成功不单独证明大文件已可下载，需用干净缓存验证一次。避免建立不保留引用的“临时素材提交”，否则将来的旧版本准备可能失效。

代码仓库对清单管理的私有资源添加明确忽略规则，不能粗略忽略整个 `assets/`。已有文件需要在保留本地副本的前提下退出当前 Git 跟踪；仅追加 `.gitignore` 不会让已跟踪文件停止上传。相应 `.import` 设置仍保留。资产仓库中的原件不放进游戏项目根目录，避免 Godot 导入和发行时扫描整套素材库。

## 5. 跨设备的日常流程

目标是授权设备只需三步：**拉取代码 → 同步锁定素材 → 用 Godot 打开工程**。

准备工具建议提供四个命令，名称和脚本路径在实施时落实，不是已经可用的命令：

| 命令 | 行为 |
| --- | --- |
| `assets status` | 检查所需版本、缺文件、错误哈希、LFS 指针未下载及本地改动，不写文件 |
| `assets sync --profile runtime` | 下载本次代码需要的游戏资源并放到清单指定位置 |
| `assets sync --profile authoring` | 额外准备本次素材编辑需要的原件与制作参数，不默认下载全部录屏 |
| `assets verify` | 检查清单、文件和引用是否一致，返回具体缺项与非零失败码 |

同步时先取得指定提交和对应 LFS 内容，再校验大小、哈希与目标路径，最后安装文件。首次克隆素材仓库可跳过自动下载，随后按 profile 拉取所需路径，避免普通编码设备先下载整个素材库。工具只管理清单声明的路径，不扫描后随意覆盖别的资源。

如果目标文件已有未收录的本地修改，停止替换并列出具体文件；先将有意修改收回资产仓库，或者明确放弃该修改。失败不得留下半套新素材：先在临时目录准备，通过后安装，若中途失败恢复本轮替换前的文件。安装过程不与 Godot 编辑器的资源导入同时进行。

本机状态文件记录上次安装的路径与哈希，用于识别旧版本多出的托管文件。切换版本时，仅移走这些已确认未修改且不再需要的文件；按项目规则放入 `.delete/`，不删除用户其他文件。引擎缓存由 Godot 自己重建，不同步 `.godot/`。

素材编辑在其权威仓库进行：改源文件／参数 → 生成游戏版本 → 检查变化 → 推送资产提交与 LFS → 更新代码仓库清单 → 同步并运行受影响场景 → 提交代码和清单。源码与素材分别提交，但由精确版本关联，不要求两仓同时完成网络推送。

## 6. 分支、提交与多人协作

主仓库采用 `main` 加短期工作分支，不再叠一条长期 `develop`。

- `main` 表示当前可以继续开发的集成版本，不代表发行验收已通过或每次提交都可以发行。
- 工作分支按任务命名，例如 `codex/typing-core`、`codex/run-continuation`。一次跨设备工作继续同一个分支，不为设备各建一条长期分支。
- 已推送、正在共同使用的分支默认不改写历史。切设备前提交并推送；另一台先拉取再编辑，不能依赖没有推送的 stash。
- 当前 Godot 分支先经过现有证据和仓库整理审查，再合入 `main`，之后从新的 `main` 按当前[实施交接](migration/AGENT-HANDOFF.md)拆任务。保留有意义的主题提交，不把整轮迁移压成一条无法定位的大提交。
- 日常功能通过 PR 合入，描述问题、行为变化与真实检查范围。单人维护不额外要求一个不存在的第二位审批者；需要多人同时修改时明确文件所有者。
- 一个提交围绕一个可解释的变化，包含对应代码、必要测试、数据及说明。不要为了“四种文件类型”拆开本应一起生效的接口与资源修改。

同一 `.tscn`、大型 `.tres` 或二进制源文件尽量由一人负责编辑；并行任务使用不同工作区和明确的模块边界。二进制冲突不尝试文本合并，保留两版供负责者选择或重新制作。Agent 不能为了处理自己提交的冲突而覆盖其他人的未提交修改。

资产仓库可以使用同名短期分支，但不要求与代码分支一一对应；代码始终通过清单固定具体提交。变动较大的美术源文件按文件认领，LFS 锁作为辅助，而非取代沟通。

## 7. 旧 Web 工程与已有历史

第一阶段继续保留 `legacy/web` 代码和文档，冻结其默认开发地位。先让当前 Godot 资源与制作工具摆脱旧 `public/audio/*.js` 等生成包装，再处理旧资源副本；不能先删依赖，留下无法运行的素材工具。

具体顺序：

1. 按哈希列出旧／新目录的相同素材，区分真正副本、不同格式和加工版本。
2. 将有效原件、加工结果和参数归到确定的权威位置，给已有游戏结果保留准确的来源记录。
3. 音频工具改为从原件、明确选段及固定转换参数生成，不再依赖未入库的旧 JS 包装。若原参数无法完整还原，先保留现有游戏音频为已选版本，不宣称重生成结果相同。
4. 词库工具与说明改为以原生 `assets/vocabulary` 或明确上游输入为权威，不再强制依赖旧目录中的另一份相同 JSON。
5. 修正 Godot、旧工具、文档与许可引用后，再移走活动目录中的重复文件；需要重跑旧版时，按映射恢复本地副本。

普通提交移走文件只整理最新版本，旧 Git 历史仍然保留内容。Git LFS 也不会因为启用跟踪就自动转换之前的提交。因此本方案将“今后正确存放”与“清理已经公开的历史”分开处理。[GitHub 历史迁移说明](https://docs.github.com/en/repositories/working-with-files/managing-large-files/moving-a-file-in-your-repository-to-git-large-file-storage)

默认不为节省当前这一级别的空间重写已发布历史。若素材审查明确要求撤回已公开的文件，再做专门的历史清理：列清涉及路径、分支与标签，准备仅受授权人员访问的 Git 与素材备份，在协调停止写入后重写并强制更新，其他设备重新克隆或按明确说明恢复。不能把“删除最新文件”或“改为私有”描述成已经撤回外部副本，也不能在本轮设计阶段执行该操作。

旧版本备份本来就包含历史素材，不算继续维护两份活动原件；其用途是恢复历史，不再作为当前制作工具的输入。

## 8. 检查、发行与备份

与 Git／资产方案直接相关的最小检查：清单引用的版本存在；所有所需 LFS 内容能下载；文件哈希一致；游戏路径没有遗漏；没有把本机配置和缓存提交；已知私有资源路径不出现在公开提交的新增文件中。以明确路径与清单检查，不建立猜测所有文件内容的复杂审核系统。

公开 PR 默认只运行不需要私有资源的检查，不向任意 PR 提供素材凭据。完整导入和相关场景观察放在有权访问素材的受信环境，验证范围遵守 [TESTING](TESTING.md)。不为了整理 Git 每次跑完整战斗、平衡或发行测试；整体平衡按当前实施方案在保留内容齐备后统一进行。

确实需要共享的截图与报告进入文档或构建附件；`.temp` 仍是本地证据目录。正式交接记录写清可复现步骤及证据边界，不能只留下另一台设备不存在的绝对路径。

发布按已验证提交打版本标签，交付 EXE／PCK 与实际素材声明，不把商业原件、编辑器源文件或完整素材库塞进发布包。开发预览明确区别于正式发行，不因上传 Release 就宣称发行验收完成。

GitHub 不是唯一备份。代码保留独立备份，私有素材备份要包含实际 LFS 对象；只有 Git 的指针或一个 Git bundle 不能恢复大文件。定期从备份抽查恢复一个旧版本。视频改用外部存储后同样保留不可变版本、哈希和备份，不以一个会被覆盖的“最新版”地址作依据。

## 9. 成本与何时升级方案

当前 GitHub Free／Pro 的 LFS 包含 10 GiB 存储与每月 10 GiB 下载流量；修改一个大文件会增加一个完整版本，下载由仓库所有者承担流量。实际余额取决于账号其他仓库，本次没有读取账号账单，不能把配额当成已确认可用余额。[GitHub LFS 计费](https://docs.github.com/en/billing/concepts/product-billing/git-lfs)

1.35 GiB 的稳定音频原件适合先用 LFS；编码设备只取约几十 MiB 的运行音频，素材编辑设备才取原件。先限制无必要的下载和重复版本，不立刻购买额外服务。

如果以后加入大量频繁重导出的视频或高容量素材库，再比较 LFS 实际存储／流量和独立存储成本。那时可以只改变同步清单的下载来源，仍保留代码提交到精确文件版本的关联，不需要重做游戏资源引用。

## 10. 实施顺序与完成标准

| 顺序 | 工作 | 完成标准 |
| --- | --- | --- |
| 1 | 按已确定的双仓库方向，逐项列资产及哈希、用途、来源、公开范围和重复关系 | 每类资产去向明确，原件／成品／缓存不混淆 |
| 2 | 建立选定的仓库与 LFS 规则，先纳入少量代表性文件 | 新设备能取得实际文件，而不只是指针；不上传未经确定的资源范围 |
| 3 | 实现版本清单、检查和运行素材同步 | 干净目录能准备本次代码所需资源；错误版本、本地改动和下载失败可识别 |
| 4 | 改造音频与词库来源，整理重复引用 | 当前资源不再依赖未入库的旧包装；原件只有一处可维护来源 |
| 5 | 完整迁入所选资产、同步另一台设备 | 两台设备按同一提交运行相同资源；回到旧提交能恢复对应版本 |
| 6 | 合入 Git 工作约定，建立受信验证和备份 | 提交、素材更新、交接和恢复流程可复现；后续实施不被资产准备反复打断 |

历史清理不是第 2 步的隐式动作，只有确有必要并明确协调后单独实施。首版不建设素材网页、复杂审批平台、自动合并二进制、全面文件锁系统或全量视频同步。

本轮只交付设计和文档入口，没有创建私有仓库、修改远端可见性、配置 LFS 跟踪、上传素材、重写历史或运行新设备恢复测试。
