# M4 完整实施方案

> 历史归档：2026-10-08 调整范围前的设计、计划或证据。正文中的要求与“下一步”不构成当前任务；当前实施见[交接文档](../../../migration/AGENT-HANDOFF.md).

M4 的交付目标是让玩家从正式首页完成 **规划天赋 → 保存配置 → 输入战斗 → 获得遗物／选择事件 → 带着变化进入下一房 → 到期恢复与试炼兑现 → 结算成长 → 再次配置**。完整天赋图、遗物关系图、普通／God 隔离和失败不改状态共同构成出口，不能以开发试验场勾选或少量演示内容代替。

本文件规定整个 M4 的执行顺序、模块边界和验收方法；天赋图算法与分配契约继续以[天赋图基础方案](M4-TALENT-GRAPH-PLAN.md)为详细依据，不另立图算法。实际接入与证据只写入[阶段总结](../STAGE-SUMMARY.md)，未完成工作只维护在 [TODO](../TODO.md)。

## 1. 范围与完成边界

| M4 必须交付 | 完成时可以直接观察到什么 |
| --- | --- |
| 完整天赋图与合法分配 | 206 项各有稳定身份；四书入口、环路、分支及三类节点可读；购买、路线应用和连带撤点真实生效 |
| 正式配置、成长与保存 | 四书配置独立；初始 2 点、普通上限 60 点；有效人工字符去重累计；保存重开、坏档恢复与版本更新规则成立 |
| 正式遗物获取 | 171 件保留遗物都有获取资格说明；奖励、赠礼、交换、演化共用资格与事务，天赋许可不能由临时能力冒充 |
| 完整事件流程 | E01–E32 均有原生定义、出现条件、具体报价、合法行动、离开和正式执行落点；没有用泛用增伤选项代替专属行动 |
| 资产与期限 | 逐份借阅、抵押、演化、出售及返还；房／章／局到期；奖励债务与试炼承诺；返还不刷新使用回执 |
| 遗物关系图与理解 | 全部保留遗物可检索，邻域和直接演化可读；固定详情解释许可、当前用途和资产实例状态 |
| 正式流程接线 | 从首页到多房、章界、最终房和结算使用同一控制器、编译器及战斗链；不是只能通过测试脚本调用服务 |

为检查 M4 的房级租约、章级抵押和最终章事件，M4 必须完成房章位置与多房转场的必要接线。先使用已经存在的正式遭遇组成有限流程，不把完整编队、Boss、三章九场内容和继续周目体验提前列为完成。它们由 M5 补全；M6 负责整体收益、成长曲线、难度门槛、长时性能和发行验收。

接线验收采用同一 `RunSession` 的两章、每章三房行程：第 1–2 房覆盖房级借还，第 3→4 房覆盖章界，第 4 房之后可选择第 5 房试炼并在第 6 房使用收益，第 5→6 房覆盖最后一个事件入口。这个规模用于暴露 M4 的所有边界，不是另一个永久玩法模式；行程是可替换 Resource，M5 扩充内容时不重写控制器。全事件分别使用可复现的合法上下文检查，不要求六房内随机遇齐 32 项。

M3 全内容的行为缺证继续保留。M4 发现的购买、获取、期限或接线缺陷在当前范围修复；与这些链路直接相关的战斗入口必须有证据。不能因此顺带宣称 377 项全内容效果、重塑后的四书手感或难度已完成验收。

## 3. 固定的业务与数据契约

### 3.1 配置与成长

- 效果以现有原生 `.tres` 为权威；附属语义只补类别、概念、数值系列和关系。不运行一次性 `import_m3_catalog.py` 覆盖现有修正。
- 本书根免费，其他书根 2 点；数值、机制、质变分别按现有 1／2／4 点起值。没有全局质变数量上限，保留明确模式互斥。
- 各主书使用同一份已赚预算、各自保存配置，不把四书投资合计扣除。换主书选择该书配置，购买另一本书根不改变主书。
- `TalentAllocationService` 是购买、撤点和合法顺序的唯一判断来源。图生成、路线搜索、UI 与出征适配共用其规则，编译器不读坐标。
- 正式出征冻结分配与天赋许可。本局遗物和临时覆盖只能改变本局构筑，不回写永久配置；正式战斗中不开放天赋重配。
- God 仅取消点数预算限制，仍检查前置、路线、模式、材料与资源规则；普通和 God 配置、进度、回执、资产及记录分开。

成长政策沿用当前候选，集中放入一个政策模块：

```text
N <= 2640:             P = 2 + floor(N / 120)
2640 < N <= 7440:      P = 24 + floor((N - 2640) / 240)
N > 7440:             P = min(60, 44 + floor((N - 7440) / 480))
```

`N` 只来自固定步已经接受的有效人工字符。手打前缀即使随后取消或主动补全，已接受字符仍是人工事实；不因施法、取消或目标变化再奖励一次。错字、echo、空格、辅助后缀、自动攻击、习字和开发试验场不增加正式成长。战败和主动结束仍结算本局已赚字符，不发未取得的胜利奖励。

跨局天赋成长与本局经验／奖励机会分开。R021 的章级额外经验政策作用于本局奖励账，不能把经验加成乘进人工字符，也不能突破普通天赋上限。候选参数作为功能起值，强弱留到 M6 统一评估。

### 3.2 状态所有权与正式接线

| 所有者 | 权威状态 |
| --- | --- |
| `TalentProgress`／`ProfileState` | 累计字符、成长结算回执、四书配置、普通／God 身份及重配诊断 |
| `RunSession` | 局 ID、行程位置、流程状态、出征许可、本局资产、奖励账、事件账及检查点 |
| `RunCombatState`／`BattleSession` | 跨房战斗资源／当前房实体与固定步；不各存一份可写资产目录或账号进度 |
| `SaveRepository` | 版本、读取、临时写入、有效备份、恢复和失败结果 |
| UI | 选中、编辑草稿、预览和显示；提交意图，不直接扣点、改血、改资产或写存档 |

目标流程为 `PREPARING → BATTLE → ROOM_BOUNDARY → REWARD → ROUTE/EVENT → READY_FOR_ROOM → BATTLE`，最终进入 `RESULT`。房内升级是 `BATTLE → BATTLE_REWARD → BATTLE` 的暂停分支，不能误当房间结束。无奖励或无事件的分支可直接前进；暂停不推进房章序号和期限。流程由 `RunSession` 明确调度，不靠多个信号的连接次序决定支付或到期。

正式获取先通过资格检查和统一交易，输出新的 `BuildSelection`，由现有 `BuildCompiler` 生成下一份快照，再在安全边界安装。仍在本房内的已付对象保留原快照；房间结束先走既有有限收尾和归档，不把到期或换构筑当作免费再次施法。

### 3.3 存档与提交

正式目录为 `user://profiles/normal/` 与 `user://profiles/god/`。第一版每种模式以一个 `profile.json` 保存逻辑快照，包含成长、配置、去重摘要、M4 必要结果记录及房间之间的本局检查点。把同次提交的扣费、资产、回执、债务和检查点写在同一份快照，避免多个文件只成功一半；不先建设通用事务数据库。

保存封套区分 `schema_version`、`content_version`、`graph_version`、`layout_version` 和修订号。`run_checkpoint` 保存正式实例、覆盖、使用回执、债务、试炼、行程与玩法随机流状态，不序列化活动 Node、执行脚本或仍飞行的旧房对象。M4 提供房间之间的恢复；房内任意帧恢复不在本阶段出口，具体按下节的阶段规则处理。

提交顺序固定为 **检查版本与修订 → 对副本完成所有支付、资产与编译预检 → 写临时档并验证 → 保留有效备份并替换 → 发布内存状态与已提交结果**。任一步失败都不发布部分交易；失败原因明确展示，可重试原意图。备份恢复后再次保存，不能用已坏主档污染最后一份有效备份。主档与备份均无效时保留文件并报告读档失败，不自动另建零进度覆盖它们。

纯布局更新不退点。内容／拓扑变化重新验证 ID、顺序和选项：仍合法的配置保留，无效配置保留原始选择与诊断、暂停出征并提供重配；累计字符与记录不丢失，不把未知 ID 映射为其他能力。God 清理只作用于 God 档案并使其旧预览失效。

### 3.4 恢复位置、结果身份与序列化

| 保存阶段 | 重新打开时的行为 | 提交边界 |
| --- | --- | --- |
| 房间之间的 `REWARD / ROUTE / EVENT` | 恢复同一候选、选中对象与未提交行动，不能重新随机抽取 | 房结果及到期已提交；打开候选时连同随机流推进一起保存 |
| `READY_FOR_ROOM` | 恢复下一房的准备状态 | 旧房清理、返还、付款和下一房上下文已完成，尚未启动战斗 |
| `BATTLE / BATTLE_REWARD` | 标记本次远征中断，保留已经提交的成长和记录，结束本局；不回到房前重复打同房 | 开放战斗输入前先保存运行标记；此阶段的保存不是可恢复的战场快照 |
| `RESULT` | 展示已保存结果或返回首页 | 相同结算不再次增加字符、点数或机会 |

正常主动结束以及可处理的关窗走固定步结束与保存；进程异常中止只能保留最后成功保存的事实，不承诺每个尚未保存字符都恢复。房内奖励暂停时仍可付款、保存与安装构筑，恢复战斗不推进期限；重新启动则按中断规则处理。这样保留房内升级行为，同时不引入完整战场序列化或房前回滚套利。

`run_id` 在创建局时生成并保存，不能从种子推导；相同种子重试是新局。`room_serial`、`attempt_id` 由 `RunSession` 发放，`BattleSession.start` 消费明确的房上下文，收口现有自行增加房序号的行为。房结果以 `(run_id, room_serial, attempt_id)` 唯一识别，首次取得后冻结；重复结果不累计，相同身份却内容不同作为错误拒绝。

人工字符有两个计数：当前房固定步的计数，以及全局已接收的房结果累计。进入结算的局累计值是已结束房总量加当前尝试的有效量，不能把单房 `manual_characters` 直接当局高水位。同一局后续提交仅补高水位增量；重开 `BATTLE` 不另造一个房身份重放已经持久化的字符。

房内交易保存当前已接受字符量，但不提前消费该房的终止结算身份；正常房末以完整结果结算。异常中断按最后持久化的本房量生成一次中断结果，同样走正式结算服务，不重新开始这次尝试。

可保存的储备采用纯数据记录：稳定交接身份、`root_id`、`source_id`、材料、`amount_q`、伤害组成、来源快照标识、claims 与 lineage。保存／预览读取这些值，不调用会消耗原额的 `portion()`、`DamagePacket.take()` 或 `import_reserve()`；读取时重新构造份额，只有实际进入下一房才转移一次所有权。储备、覆盖、实例和嵌套数组都必须独立复制，不能把 `Array.duplicate()` 当作业务对象的深复制。

检查点还须覆盖 HP、护盾、共鸣、储备停用词数、待执行开场附加、尚未领取的资产效果、奖励余额、待选报价及用过的事件。随机流状态等需要精确保存的 64 位值使用十进制字符串编码；固定点资源按既有范围校验。纯布局升级可继续本局；内容／图版本不兼容的本局不在新规则下静默重放，保留成长及结算记录，给出无法继续的具体原因和重配入口。

### 3.5 交易必须同时覆盖资产、效果和未来返还

`CombatAssetService.prepare` 当前每处理一个动作都会编译。多资产交换应增加具名批量请求：复制一次 → 校验引用与支付 → 在副本应用全部移除／替换／添加 → 编译最终状态一次。单动作接口可复用这一实现。不能把多个 `prepare` 结果逐个发布，也不能要求中间那个尚未补回能力的构筑必须合法。

房内交易在完整固定步之后暂停，取 `BattleSession` 当前生命与资源制作快照；房间之间取已提交的交接状态，不能拿尚未同步的 `RunCombatState.hp_q` 报价。暂停保持到保存和准备好的结果安装完成，提交后由战斗所有者发布新构筑与一次效果；不能先落盘再放入一条可能因状态漂移被拒绝的普通命令。

取得资产时，一次性治疗、充能和获取性长期效果应进入同一事务结果。把当前战斗入口中的获取计算提取为可预览的有限效果计算：房间之间的治疗直接改变候选 HP 并记实例回执；需要实际战斗承接的效果保存为具名待执行项，在入房时领取一次。编译、加载快照和返还都不重新触发获取。降低生命上限后按新上限截断当前生命，到期只恢复上限，不能补回被截断的生命。

本局资产总表包含抵押中实例；送入编译器的是当前有效实例投影。抵押期间保留层数／唯一性和归还权占位，获取检查不能把它当作彻底卖掉后重新发一件。租借结束与抵押返还同时发生时，对最终有效集合做一次提交；新交易若会让已承诺返还后的层数或模式非法，应在报价时拒绝并说明冲突，而不是到期再丢物品或刷新实例身份。

E10、E14、E25 等实例改造另需有限的 `AssetVariantDefinition` 与实例 `variant_id`：引用已登记的替换规则、继承预算和参数，不增加任意表达式。编译按该实例的完整有效定义计算，替换的父效果不再叠加；其他同类实例不受影响。它与目录中由 `replaces` 声明的常规演化分别校验，不把全局 `CombatBuildOverride` 当作单件工具变体。变体、实例 ID、使用回执和期限一起保存。

变体不免除特殊遗物许可；临时借到的能力仍用明确期限的覆盖或合法借物表达，不能经变体身份转成永久特殊资产。

### 3.6 报价、机会和随机数

首次打开奖励或事件时生成稳定 `offer_id`，冻结候选及其数值、相关本局修订与生成后的随机状态，一起保存。选择目标后形成绑定该实例的最终报价。返回页面、重新打开或保存失败重试沿用同一候选；查看详情与不合法点击不消耗随机数。

取得结果后保存提交回执；重复提交返回该结果，不能再次付费、治疗或领物。修订改变则在同一选择入口重新预检并展示报价；不因刷新过期报价免费换一组随机物品。永久资格、实际使用条件、层数与对象绑定必须全部满足，不能只看最终编译通过。

本局账分开记录已赚机会、已用机会、待偿债务和未来可承诺容量。未来容量取“完成既定剩余行程、不依赖随机掉落、可失效加成或未通过试炼时必得奖励”的保守下界，扣除已经预留的债务。R021 额外经验与试炼收益只有实际兑现后进入已赚账，不能预先为更多债务提供担保。死亡／主动结束关闭未发生的本局承诺并记录，不扣跨局天赋点。

战斗按唯一敌人／收益事件身份提交具名 `RewardFact`，携带基础经验和政策上下文；现有 `kills_by_source` 汇总不足以还原敌人种类与经验。奖励系统消费事实一次、扣除已偿债务、累计经验并产生机会，房末只核对摘要。R021 若在房内取得，从之后符合条件的事实生效，不能到房末再给取得之前的击杀补加成。候选抽取不发布经验，查看战报也不重新消费击杀事实。

事件路线本身带一个明确的机会预算，A／B／C 都消耗或转换这次预算，离开也完成该路线选择；C 不是另一份额外奖励。E31 先绑定出售对象，再按“出售后的资产集合”生成合格候选，最终一次提交出售与所选奖励；取消最终交易不先卖掉物品，重复进入同一事件也不重新抽奖。未来债务仍单独计账。

### 3.7 房章边界与事件可发生性

边界同时保留 `completed_room` 和 `next_room`。旧章最后一房结束后，先按旧章规则清理及到期，再建立下一章位置、生成面向下一房的事件。报价显式记录受影响的房／章；“当前章”始终是报价中显示的生效章，不能把跨章入口的新租约立刻过期。

每个契约记录 `activation_room`、`expires_after_room/chapter`、对象身份、执行次数及领取记录；现有 `expires_at` 类别不足以表达完整日期，需要由 M4 契约补齐。跨过边界时先收集到期与激活结果，再共同计算、编译、保存，不能按数组删除顺序决定生效结果。

试炼先采集真实胜利事实，完成旧房收尾及到期后，再激活只对后续有效的奖励。不用新获得的回收效率重新计算刚结束的房间，不向已经消费的材料补发返还。报价要求试炼完成后仍有实际使用收益的房间；只剩最终房时，依赖下一房通关后长期生效的行动不合法。E32 可在最终章且尚有战斗时出现，最终房已经结束则直接走结算。

事件所需事实由正式链提供：能力与材料来自编译快照，资产来自本局总表，词库匹配来自词库查询，真实中断／同根多份等已发生事实由战斗结果提交。历史事实仅证明发生过，不创造可消费的标记或储备。每项事件还要证明“出现时点存在符合条件的正式状态”；登记 32 个 ID 和人工注入状态不足以证明事件都能遇到。

### 3.8 内容政策与事实契约

| 条目 | 当前证据与缺口 | 实施前需要形成的结果 |
| --- | --- | --- |
| R021 额外经验 | 生效期间取得的合格基础经验增加 35%；每章额外经验最多为该章预定基础经验总量的 25% | 入章前冻结基础行程经验总量，事件增加的敌人不抬高上限。按累计经验计算并保留小数余量；停用期间不累计，取得前收益不追溯，借还或更换实例不重置章累计。额外经验进入本局奖励进度，不增加人工字符，也不提前担保未来债务 |
| E17 聚字校勘 | 资格为本局曾真实产生可兑现标记；实际标记仍属于原房词会话，不跨房保存为可消费资产 | 在正式标记创建提交处记录 `has_created_redeemable_mark`，由房结果汇入本局事实并随检查点保存。事件仍在房间之间出现，A／B 只改变生效期限内后续新标记的用途；能力存在或人工字符数不能代替这条事实 |

R021 与 E17 按上述已确定契约实施，候选卡与接口说明使用同一口径。R021 参数作为 M4 功能起值，整体收益在 M6 统一评估。

## 4. 逐步实施

按下列主顺序推进，每一批取得出口证据后进入下一批。步骤 12–13 按事件批次共同迭代：先补该批所需的最小期限调度，再验证行动及到期。只有出现真实业务冲突或共享接口不够表达时才回到设计，不在普通文件选择、参数接线或排版细节上反复等待确认。

### 步骤 01：锁定输入与接线清单

1. 核对工作区已有改动和内容 ID；形成 206 项图输入、171 项获取输入、32 个事件的覆盖索引，记录正式源文件与已有接口。
2. 将采购成本、成长公式、权限和期限语义汇入实施输入；明确候选参数的来源，避免实现时重新猜测。
3. 记录当前空配置出征、结果页占位、无房章控制器及无账号档案的实际缺口。
4. 为第 3.8 节的 R021 明确所缺参数与处理时点，为 E17 明确真实事实的生产位置；不得用接口存在代替内容定稿。

产物：开发证据目录 `.temp/godot-m4/baseline/` 的输入摘要和哈希；必要的附属数据定义。核对无缺失／重复 ID，效果、费用和前置没有被改写。此步不跑旧全量测试或 Godot 全套检查。

### 步骤 02：补齐全部天赋图语义

1. 在 `game/content/talents/` 定义节点类别、数值系列和语义 profile，书根仍引用 `BookDefinition`。
2. `tools/graphs/` 读取正式目录和附属 `talent_semantics.json`，补全概念、对象、操作、材料输入输出与少数明确关系。
3. 覆盖全部 122 个独立数值实例；每个实例保持自己的 ID，不压成可反复升级的 30 个点。
4. 区分成长邻接、AND／OR 购买前置、运行使用条件、模式、许可与演化；用途查询复用编译能力，不新增另一份战斗公式。
5. 附属 JSON 是作者输入，生成 Resource 是只读产物；输出稳定排序、输入哈希与字段来源，避免两边手工维护。图输入先建立图标身份和轮廓占位，详细材质随后实现。

出口：206 项完整、有来源的结构化输入；未知概念、漏项、重复与坏引用被拒绝；补数据前后原生效果哈希一致。依赖步骤 01。

### 步骤 03：实现分配服务与编译适配

1. 在 `game/progression/` 实现 `TalentAllocation`、具名选择、上下文和预览结果；预算政策独立于 UI。
2. 实现 `inspect_node`、`preview_add`、`preview_remove`、`validate`；从免费主书根正向重建真实购买顺序，不仅检查最终集合连通。
3. 撤点输出全部连带变化；有替代路径的合法节点保留。缺失 T58 清形状，K19 材料失效返回待重选，不能自动替玩家选择或删除 K19。
4. 合订、副书、独卷形状与校准材料先选择再提交；多节点路线整体预览，不购买半条路线。
5. 适配为 `BuildSelection`，规范化书根，主书规则仅编译一次；保留现有开发试验场的独立配置入口。
6. `commit` 的正式持久化接线在步骤 07 完成，之前只验证内存副本与修订契约。

出口：真实小图覆盖预算不足、AND／OR、模式、循环依赖、替代通路、连带撤点、材料重选、God 及失败不改状态；合法结果进入同一战斗编译器。计划新增 `test_talent_allocation.gd`，其目标是保护分配契约。依赖步骤 02。

### 步骤 04：局部图形与开发观察

1. 按天赋图方案实现稳定归组和数值分配；机制群目标 4–10 项、初始上限 12，不为了对称复制或丢弃内容。

4. 在 `development/talent_atlas_lab.tscn` 展示候选、冲突和购买结果；与步骤 03 的服务共用判定。

出口：至少能观察不同构造和实际购买，无逐节点手填坐标、无额外收费点。小图只用于尽早暴露方法问题，随后必须扩至完整输入。依赖步骤 02–03。

### 步骤 05：完整生成、路线见证与发布

1. 以四书约 0.4R 的锚点安排整组位置，生成近邻组间边、绕行和环路；不退化成四个封闭扇区或唯一中央枢纽。

4. 验证初始 2 点机制入口、普通 60 点内路线、模式移除后的主干、单点断路及沿途用途；报告相邻／对侧费用，不把 8–14／14–22 候选值当硬性平衡结论。

出口：完整 206 项候选全部覆盖、重复生成哈希一致、实际路径零交叉且无遮挡、合法路线有顺序与真实费用。计划新增 `test_talent_graph.gd`；生成报告与失败候选留在 `.temp/godot-m4/graphs/`。依赖步骤 03–04。

1. 实现 `AcquisitionService.evaluate` 与具名上下文，读取冻结天赋许可、实际资产／使用记录、当前能力、模式、词库范围及渠道。
2. 为全部 171 件补必要的附属获取定义；已有主书限制、许可、层数和演化字段继续引用原生定义，不复制数值。条件按可产生的对象判断，不要求菜单打开时恰有燃烧敌人。
3. 永久奖励、赠礼、交换和演化共用资格。基础探索入口开放；特殊遗物无实际天赋许可不能入池。临时能力到期不会删除已永久取得的资产，只暂停缺条件的效果。
4. 实现本局经验／奖励机会账和独立奖励随机流；追踪已发生的击杀或合法收益事实，一次奖励消耗一次机会。抽取无放回，适度关联权重、多样性和层数检查分开；合格不足时少给选项或合规补给。
5. 普通奖励初始 1 次机会、8 BP 制作标尺；经验阈值与每种正式敌人的基础经验一起写入 `RewardPolicy`，不得使用未定义敌人的默认经验兜底。旧执行链初值为阈值 27、后续 `round(previous * 1.13 + 4)`；这是待对照的输入，采用或调整必须留下统一政策版本。本局经验不改变第 3.1 节成长口径。
6. 先完成第 3.8 节 R021 的内容定稿，再将额外经验按章唯一累计。不能按每次房末请求重发同一章收益，也不能把其预测额外机会算入可承诺债务容量。返还同一资产或更换实例不刷新已经使用的章上限。
7. 先实现同一 `RunTransactionService` 的单份获取提交：预检资格、机会、一次获取效果及编译，保存成功后发布资产与新快照。步骤 11 在这条提交链上扩展冻结报价和多资产动作，不让奖励 UI 另写付款逻辑。
8. 房内升级在固定步提交后暂停规则、冻结候选，提交成功后回到同一房；房末奖励则先完成房界，再打开候选。待选页按第 3.4 节区分能否恢复，不使用同一个模糊的“安全边界”描述两者。
9. 原生奖励页保留可读说明、层数变化和独立遗物图形。图标身份从步骤 02／06 的共用基础接入，步骤 14 补关系图，不把奖励可辨识性全部推到最后。

出口：每件遗物有合格／拒绝理由；无许可、满层、主书限制、重复无增量、演化父实例及合法新入口均可解释。实际奖励进入下一房；重复选择不扣两次或发两份。计划新增 `test_acquisition_rewards.gd`。依赖步骤 09。

### 步骤 11：冻结报价与原子资产事务

1. 实现 `FrozenOffer`、`EventContext` 并扩展步骤 10 的统一 `RunTransactionService`；UI 先选具体资产，再冻结最终报价。
2. 报价携带内容版本、本局修订、房章位置、许可版本、具体实例、覆盖／模式、支付数字、机会债务、期限、恢复方式和挑战请求。
3. 当前生命、上限、真实储备、资产、模式或行程变化均使相关报价失效。返回 `STALE_OFFER` 后不扣费，重新展示有效报价；重复提交不重复领取。
4. 按第 3.5 节增加批量资产请求与非消费的纯数据副本，完成全部变化后只编译最终状态。把 R012 等一次效果纳入候选状态；保存后只有发布动作，没有第二段可能重新判失败的付款。
5. 对抵押／返还维护 `owned / leased / pledged / returned / replaced` 状态和返回权占位，实例身份与使用回执不变；E13 开场附加从真实储备转移所有权，重新打开报价不提前减少储备。
6. 补齐有限资产变体，使 E10／E14／E25 可以只改指定实例；对普通目录演化与事件变体分别验证，最终效果与继承预算可解释。
7. 按第 3.6 节预留未来奖励的保守容量；同一机会不能偿两笔债。首次候选、过期重报价、取消以及重复提交分别有稳定结果，E31 出售加选奖作为一个事务完成。

出口：过期、重复、对象消失、编译失败、余额不足及保存失败均不留下部分扣费；演化／返还后一次治疗、复起与充能不会刷新。计划新增 `test_event_transactions.gd`，复用 `test_m3_assets.gd` 的相关实例契约。依赖步骤 09–10。

### 步骤 12：逐批接入全部 32 个事件

在 `game/content/events/` 写原生 `EventDefinition` 与具名行动模板，正式参数来自[候选卡](../build-system-design/appendix-event-candidates.md)、[参数标尺](../build-system-design/05-CONTENT-CATALOG.md#6-候选参数的初始标尺)和 [M3 接口表](M3-INTEGRATION.md#事件和获取交接)。每项先形成“条件 → 绑定对象 → 参数／支付／期限 → 提交 → 到期 → 证据”的记录，再进入正式出现池。

先完成 E01（模式与上限恢复）、E04（临时能力与许可）、E31（抵押／出售与选奖）、E23（试炼后激活）四条纵向流程，与步骤 13 共同验证。通过后再按下表补全；表格是覆盖分组，不要求先写完 12 个模式事件才第一次测试借还。

每个行动记录至少包含：出现阶段、具体条件、对象筛选、效果与代价的参数键／单位／数值、一次或持续、生效房／到期房章、机会来源、许可要求、变体身份、失败原因与最小合法情境。公开遭遇要求列出具体组成或规则差异。E17 通过真实输入与标记创建取得本局资格，不能只向测试状态塞一份标记宣称接通。

| 接入批次 | 事件 | 重点出口 |
| --- | --- | --- |
| A：模式与同池交换 | E01、E03、E07、E11、E12、E15、E16、E18、E19、E27、E29、E30 | 只覆盖登记模式／池；上限、形状和材料真实变化，代价与到期恢复可解释 |
| B：临时借阅与期限 | E02、E04、E05、E06、E26、E28 | 明确下一房／本章／本局；不授永久许可；已有已付过程和新对象边界成立 |
| C：储备、资产与演化 | E09、E10、E13、E14、E17、E25、E31 | 消费真实余量、玩家选实例、父效果移除、抵押返还与使用回执保留 |
| D：公开挑战、债务与最终章 | E08、E20、E21、E22、E23、E24、E32 | 挑战与收益共同报价，试炼成功后激活，失败不激活，最终房不产生无后续的债务 |

每项落实 A／B 两种构筑行动、基础 C 和离开；无效行动隐藏或明确不可选。只有至少两种行动合法且有实际变化，并有可靠基础行动时才入池；恢复已满、无目标交换和不存在的未来奖励不能凑数。

“更多／更少”逐项绑定明确参数键和数字；借用原生操作，普通幅度沿现有候选标尺。涉及尚未登记的变体先明确对象与 BP 去向，不私自解释成所有属性加成。只有需要改购买前置、删内容或改变候选业务语义时提交具体冲突与方案。

事件页使用固定标题、操作与内部滚动正文；展示对象、收益、代价、期限和挑战，正文不泄露执行器术语。离开也保存为一次选择，不给刷新事件或重抽收益。

出口：32 项覆盖表包含全部行动的合法结果、拒绝原因、期限及正式执行落点；控制器有真实出现池，定向检查可指定上下文复现每项，不以随机试玩遇不到为由跳过内容。计划新增 `test_event_catalog.gd`，同一测试按事件批次选择检查，不逐件起平衡脚本。依赖步骤 11，各批同时接步骤 13 所需生命周期。

### 步骤 13：统一期限、试炼与终局清理

1. 房级从下一战斗房开始，到该房收尾后结束；章级覆盖明确的当前章剩余房；菜单、暂停和事件页不消耗租期。
2. 房／章界统一顺序：旧房有限收尾与归档 → 冻结结果／试炼成功事实 → 撤销到期覆盖、移除借物和返还抵押 → 激活对后续有效的试炼奖励 → 编译最终构筑 → 保存同一检查点 → 打开奖励及面向下一房的路线／事件。先处理旧章，再按新位置生成新章报价。短期限收益必须仍有适用后续，否则报价不合法。
3. 到期只恢复上限和空间，不免费治疗、制造法术或返还已花机会。永久与临时同种实例分别处理，移除指定租约不误删永久资产。
4. `TrialContract` 绑定具体下一房和公开挑战；只有该房真实胜利才激活对应收益。战败、主动结束或错房结果不兑现，失败原因与已付代价记入本局结果。新获得的回收能力不追溯刚清理的房间；无后续使用房间的试炼在报价时排除。
5. 挑战复用现有近敌／后排、弱敌围护、连续波次、分散、耐久和弹幕入口；需要的最小公开压力写入遭遇请求。完整 Boss 与三章编队仍由 M5 负责。
6. 清房和章界不重发 R021 奖励，偿债先于下一次报价；最终结束移除本局覆盖／借物并闭合契约，保存必要记录而非把本局能力带入下一局。

出口：同种永久／临时并存、到期同回执返还、章末上限恢复、试炼成败、重复边界、最终章及读取检查点均正确。追加 `test_run_progression.gd` 的边界情境，并定向复验 M3 资产／跨房检查。依赖步骤 11–12；不另建第二套期限计算。

### 步骤 14：完整遗物图与统一说明

1. 从天赋图已成熟的变换、检索、点击及固定详情提取确实共用的部分，不提前建设通用图编辑器。
2. 为全部 171 件按概念／操作邻域和直接演化生成静态关系图；成长、演化、许可和事件引用保持不同语义，详情关联可定位，不全绘成交叉线网。
3. 同一遗物的图鉴、奖励、事件及关系图共用稳定图形映射；不使用 emoji 或一枚通用图标冒充所有遗物。M4 可见内容需可辨识，完整插画与全局素材收束留到 M5。
4. 固定详情展示当前资格、许可、条件、层数、实例来源／租约和演化结果；没有取得仍可预览，不把图鉴当第二张收费树。
5. 更新必要指南和 M4 操作说明，使玩家能理解点数、许可、借还、期限与同池代价；不顺带重写完整教学或全战报。

出口：全目录可检索、独立图形可辨、演化路径与实例状态准确；奖励／事件详情与真实提交数字一致。实际窗口检查遗物图、长文滚动、选中切换与页面往返。依赖步骤 06、10–13。

### 步骤 15：正式闭环与 M4 收尾

1. 从正式首页完成普通四书的初始 2 点购买与战斗，另以合法已赚预算走一条跨书路径、一次模式选择和连带撤点。
2. 走正式多房流程：正常奖励 → 普通工具开启新方向 → 租借／抵押 → 下一房试炼 → 章界返还 → 最终结算 → 重开恢复。特殊许可用两份真实出征配置分别检查入池差异，不在本局中途凭借阅取得永久许可。不能以试验场勾选代替。
3. God 独立重复配置、获取、期限与清理；确认普通进度和本局记录不受影响。
4. 按目录情境验证全部事件与获取覆盖，审查 UI、日志、失败结果和证据范围；检查角色输入、暂停和设置回归，不无理由跑全量测试或发行导出。
5. 更新阶段总结、实现快照、接口说明与 TODO，明确 M4 完成证据、M3 剩余缺证以及 M5／M6 交接。通过实现和检查可报告工程结果，实际观感与手感结论按真实观察记录，不代替用户确认。
6. 本次不再需要的临时文件按仓库规则移入 `.delete/` 对应子目录；保留可复现报告、有效截图和失败证据，不动其他任务改动。

出口：第 1 节全部成立，有可从首页审查的结果、覆盖表与证据。达到出口后停止扩展，不合并 Git／私有资产建设、无关卡顿排查或发行工作。

## 6. 验证与证据口径

上述测试名称均为拟新增的、有回归价值的 M4 检查。开始前确认现有验证是否已能覆盖，按真实职责合并或复用，不为每一步另造诊断脚本。使用锁定 Godot CLI、实际 `InputEventKey.unicode` 和正式控制器；图形／日志观察按[工具链](../../../migration/TOOLCHAIN.md)与[验证范围](../TESTING.md)进行，MCP 只操作生成预览副本。

| 检查族 | 要证明的内容 | 不能据此宣称 |
| --- | --- | --- |
| 目录与生成 | 完整身份、效果未被导入器覆盖、哈希确定、实际路径／标签几何及购买见证 | 玩家已看懂全图或全部节点划算 |
| 分配与路线 | 真顺序、选择、预算、撤点、旧预览失效及原子应用 | 已找到绝对最优路线，除非有证明 |
| 保存与成长 | 有效字符口径、去重、失败恢复、版本、普通／God 和检查点 | 房内任意帧恢复或旧浏览器数据迁移 |
| 获取与事件 | 全渠道资格、真实报价、全行动、实例与机会唯一消费、期限／试炼 | 每项战斗效果的全部情境或统一收益通过 |
| 正式应用与窗口 | 首页闭环、真实字符入口、图谱／奖励／事件交互、动态中断与画面 | 完整三章九场、五档难度或长时性能验收 |

证据按职责进入 `.temp/godot-m4/`，每份报告记录输入哈希、代码状态、引擎／运行方式、通过／失败／未覆盖及对应路径。事件报告逐项记录 E01–E32 的行动和边界，获取报告逐项记录 171 件资格及正式渠道；总通过数量不能替代覆盖范围。

以下反例并入对应的现有或拟新增检查，作为关键契约的最小回归，不单独增设测试工程：

| 情境 | 必须观察到的结果 |
| --- | --- |
| 两房分别输入 100、70 字，第二房结果重复提交 | 局累计 170，第二次同回执增量 0；不是把 70 当作新的局累计 |

| 同一事务去掉旧工具、补上替代工具，中间状态不完整 | 按最终状态判断；合法交换可提交，不会先移除原物再失败 |

资料不足、有限搜索未找到和明确不合法分别报告。不得用旧图、旧截图、不同失败运行里的通过项或历史 M2 验收填补本轮缺证。文档阶段只审阅内容、差异与本地引用，不运行游戏测试。
