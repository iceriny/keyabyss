## 基线与取舍

2026-10-10：核对研究时保存的会话与法术源码，和当前基线一致。此前隔离试验只作为选项筛选依据，正式实施继续以此提交重做回归与端到端验证。

- 采用页 ID 索引、单目标线性择优、无回调清弹稳定压缩和循环内不变量外提；保留有序范围快照、死亡对象身份和同步连锁。
- 单命中投射物保留精确扫掠，择最早接触；贯穿保持先收集、排序、顺序提交。
- 实体分离平方距离预筛在此前稀疏／拥挤对照中收益不稳定，保留原四轮求解。暂不引入空间网格、全局存活缓存或碰撞框架。
- 自动闪避的纯 GDScript 连续缓冲试验只有约 7～14% 改善，256 弹仍超过操作预算；继续验证批量 .NET 评分。轨迹预测及候选常量仍按原 GDScript 表达式计算。

## 实施与验证

实施中按阶段补充实际结果；性能样本、完整日志与基线引用保存在 `.temp/combat-implementation-20261010/`。运行代码、工具链、规则一致性、窗口表现和发行依赖分别记录，不把微基准提速视为整帧提速。

### 查询与评分接入

页索引由原生成／重开入口维护，夹具的直接追加同步登记；死亡不删索引。首击选择复用原命中提交循环，只为最终选中者生成一条接触记录；贯穿维持原快照。电链局部可达范围、清弹边界继续使用原 `length()` 比较，未用数学等价的平方比较改变阈值舍入。

.NET 采用一个同步 `Choose` 批次，内循环只使用托管数组；GDScript 仍持有所有实体、轨迹积分和原事件。首轮冷测发现 256 弹首次操作约 14.7ms，而稳定 p95 约 5.1ms；首次 JIT 不能留到玩家按键。因此将纯数值路径的一次准备放到战斗会话构造，后续复测分别报告会话准备和首次实际操作。每次跨语言调用约分配 37KB，600 次出现 2 次 Gen0 回收；不能宣称复用 GDScript 缓冲等于零分配。

单独预热 C# 方法没有消除首次封送的成本，最终改为在 GDScript 会话构造中执行一次小型合成批次，覆盖实际调用边界。数值程序集在 Debug 与导出均启用优化并保留调试符号，避免开发检查和发行采用不同编译优化条件。准备后会话创建加起局约 113.2ms，首次 256 弹选点 6.32ms；稳定 p95 4.59ms、p99 5.00ms、最大 5.87ms（`cold-final.log`）。起局耗时含资源与构筑初始化，不能全部归因于 .NET。

几何专项暴露了基线夹具的动量断言问题：高速碰撞先追加碰撞伤害的受击冲量，夹具却只按输入冲量检查守恒。通过已有 `counter_push_time` 状态隔离该伤害回调，保留原质量交换、2400 动量目标及容差，未修改物理求解。新增同时间字符串 ID 首击、贯穿击杀塔后解除 Boss 盾、分裂子体不加入原接触快照的边界案例。

### 性能取舍

本机 Ryzen 7 3800X、headless，Debug GDScript 与优化后的数值程序集，固定输入交替 A/B，预热后每组合 3×200 次。以下参考为连续缓冲 GDScript 版本，计入完整 `_safe_direction()`、封送与返回，单位 ms（`native-final.log`）：

| 场景 | GDScript p95 | .NET p95 | .NET p99 |
| --- | ---: | ---: | ---: |
| 无敌弹 | 0.110 | 0.179 | 0.226 |
| 随机 32 弹 | 1.764 | 0.514 | 0.608 |
| 随机 128 弹 | 4.155 | 1.085 | 1.251 |
| 随机 256 弹 | 19.319 | 3.715 | 4.000 |
| 环形 128 弹 | 10.991 | 2.309 | 2.660 |
| 环形 256 弹 | 22.640 | 4.525 | 4.756 |

128／256 弹达到降低至少30%且节省1ms的采用门槛，无弹回退0.069ms在0.1ms限额内。环形256弹仍未达到4ms的p95目标，保留这一残余成本；不缩短预测、不减少方向或改视觉来凑预算。本机结果不替代目标CPU实测。

实体分离保持原算法，8／24／40个实体稀疏与拥挤位置对照一致；不引入网格与平方预筛。当前优化的重点是索敌与输入操作峰值，不宣称消除所有碰撞或GPU开销。

100个历史对象、24个存活对象的ID查询中位从0.00949ms降至0.00138ms，重定向中位从0.11815ms降至0.04390ms。四书稀疏／拥挤各360步，计时排除对照序列化；步骤中位约降低6～7%，p95由2.82～3.33ms降至2.62～3.04ms。此为固定夹具中的总步耗时，不含窗口渲染，也未制造大量在飞弹来放大首击选择收益。

### 规则与构建检查

- 从基线提交生成参考子类，最终4,279项检查零差异：1,152个自动闪避输入、四书两种分布共2,880步以及查询契约；逐步比较事件顺序、敌人、弹道、范围场、纸灵、危险区、效果状态和资源／RNG。实际回放同时包含人工字符、御术和自动闪避。
- 几何专项与防御／移动／慢时间检查均0失败；受影响9个GDScript及依赖检查无警告／错误。几何夹具的有意整数截断使用局部注解保留原运算。
- `Debug` 数值程序集构建0警告／0错误；依赖按 Debug、ExportDebug、ExportRelease 分别锁定，后两者包含win-x64恢复图。首次预览导入在完整输出后原生退出，图形导入也未能消除问题；导出明确报告缺少 `.sln`。补齐解决方案及三个配置后，预览副本独立编译、headless导入均退出0（`preview-final.log`）。

### 窗口与发行交付

Forward+／RTX4070 SUPER／1920×1080 的四书窗口覆盖真实字符施法、强化、终式和自动闪避；退出0，无脚本／shader错误，21张采样图在 `.temp/godot-m2/presentation-4554187/`，已查看四书代表帧。御术／慢时间专项14项通过，截图在 `.temp/defense-slow-20261009/window-4118997/`，已查看完美御术帧。日志分别为 `four-books-window.log`、`defense-window.log`；没有改动 `app/`、`ui/`、视觉／音频资源或渲染质量。这些检查确认局部表现和事件投影，不替代真人完整遭遇体验。

导出过程中修正了两项工具链前提：补齐 `.sln`，并用 `--screen 0` 避免旧编辑器记忆中的显示器编号。进一步发现官方成品模板忽略 `--script`，直接调用GUI成品执行Boss脚本的旧方法实际启动首页，不能算资源检查通过。已改为编辑器加载成品PCK运行资源检查，再独立执行成品控制台包装器、隔离APPDATA、等待异步首页准备。Release需要将控制台包装器设置为“Debug and Release”。这些修正只涉及交付验证。

最终 Debug／Release 导出均退出0、真实Shader Baker完成、锁定托管发布成功，成品PCK的三个Boss五档资源检查0失败，独立成品到达 `Keyabyss ready`（`export-debug-verified.log`、`export-release-final.log`）。PCK检查用当前Debug程序集，不能声称它执行了Release算法。headless自动退出仍报告85个ObjectDB实例未释放；此前纯GDScript测试包已有84个，不把本轮结果写成无警告或把新增实例判定为已定位。

Release另在仅保留Windows系统PATH、`DOTNET_ROOT`指向不存在目录、关闭多级查找且隔离APPDATA的环境中，以真实Forward+窗口启动900帧，退出0，无引擎错误。进程模块确认 `hostfxr.dll`、`hostpolicy.dll`、`coreclr.dll` 均从成品 `data_Keyabyss_windows_x86_64/` 加载（`release-no-sdk-engine.log`、`release-no-sdk-modules.log`）。这验证了受限搜索环境与自带运行时；没有卸载本机SDK，不能替代干净目标机验收。没有在成品中完成整局操作。

自包含目录携带 .NET 8.0.14，187个文件共79,756,197字节（约76.1MiB），其中业务 `Keyabyss.dll` 为10,240字节；这是新增托管运行目录大小，不是整包压缩增量。开发SDK锁为9.0.201，玩家运行不依赖开发SDK。保留上游运行时许可和第三方声明并随导出复制；交付代价与性能收益一并接受。
