# 键渊｜Godot 技术路线与 Agent 开发指导方案

## 一、总体方向

**以 Godot 原生能力为中心，对键渊进行面向桌面平台的整体重构，形成架构合理、画面精致、运行流畅、易于持续开发的游戏工程。类型化 GDScript 承担主要业务，C# 按需补充；延续既定的玩法、构筑与成长方向，以及 UI 的视觉身份。**

重构应当利用游戏引擎重新组织运行方式，而不是让 Godot 充当旧 Web 项目的容器。面向原生桌面的渲染、计算、资源管理和并行工作进行设计，充分利用目标平台的能力。保留的是游戏定位、已确定的设计逻辑、内容价值和视觉身份，不是浏览器时代的架构、时间循环、平台适配或运行轨迹。

运行效率、画面质量、操作体验和开发维护共同构成技术决策的依据。性能与硬件利用能力的改善，应当来自适配新平台的架构、合理的计算组织和引擎能力的有效使用，并与更丰富的画面表现相协调。不能为了单一指标压缩玩法、牺牲 UI 风格或把所有设备的画面上限压到最低档；也不把启用更多高级功能等同于更优设计。

项目面向桌面键盘与鼠标操作，Windows 为优先开发和发布平台。不支持浏览器与移动端，不进行 Web 导出，也不保留旧版运行轨迹等价要求。其他桌面平台在形成明确发布需求后再扩展。

### 总体技术选型

| 领域 | 推荐选择 |
| --- | --- |
| 引擎 | Godot 4.x 稳定版，使用 .NET 版编辑器 |
| 主要语言 | 类型化 GDScript |
| 辅助语言 | 按需引入 C#，不从一开始广泛混写 |
| 游戏与表现体系 | Godot 原生 2D、场景、资源、动画、音频及界面体系 |
| 主渲染路线 | Forward+，以 HDR 2D 建立高质量表现基线 |
| 画质策略 | 同一视觉设计下提供不同表现成本的画质等级 |
| 分辨率策略 | 1920×1080 设计基准，统一可调的游戏分辨率体系 |
| Agent 主入口 | Windows 本地 Codex，以 CLI 为执行基础 |
| 引擎自动化 | Godot 官方 CLI 为基础，单一主 MCP 补充运行时能力 |
| 主 MCP | tugcantopaloglu/godot-mcp |
| 指令与知识 | 项目级 AGENTS.md、少量按需加载的 Skills、对应版本官方文档 |

工具名称是当前选型，不是游戏架构必须永久依赖的组成部分。开发工具可以替换，游戏工程保持独立。

## 二、引擎、语言与架构原则

### 引擎版本保持一致，语言逐步扩展

采用已发布的稳定版本，并为项目固定明确版本。编辑器、导出模板、文档和插件兼容范围围绕同一版本管理，不将开发预览版或第三方工具声称支持的“最新版本”自动作为升级依据。

.NET 版编辑器支持 GDScript，也支持同一工程使用两种语言。选择它是为未来保留 C# 能力，不要求从第一天创建 C# 业务代码。引擎及所需开发环境按选定版本的官方要求配置；引入 C# 脚本或需要编译的 C# 插件时，再为工程接入对应的程序集构建流程。.NET 版编辑器不会自动提高 GDScript 的执行速度。[^1][^2]

### 以类型化 GDScript 为主，不以动态化换取表面简洁

主要业务优先采用 GDScript，以统一场景、脚本与编辑器的开发方式。公共接口、重要数据和容易产生歧义的边界使用明确类型；局部变量可以合理利用类型推断，不把“每个变量都必须重复声明类型”变成形式负担。

核心概念采用具名类型与清楚的数据结构，避免把整个项目组织成随处传递的字符串字段和动态字典。类型标注与相关警告用于帮助开发者和 Agent 发现错误，而不是在出现问题时通过删除类型约束绕过诊断。GDScript 的静态类型还可以在操作数类型已知时启用更优化的操作码，但它并不等价于 C# 的完整类型体系或执行性能。[^3]

### 以 Godot 原生组织方式为中心

以新平台上的综合适配性为标准，选择 Godot 原生场景、节点、资源、信号、动画与生命周期能力，形成适合当前游戏的组织方式。组合优先，系统职责清楚，数据来源明确。

现有架构是理解玩法与已有工作的参考，不是必须保留的约束。保留、拆分、替换或重新组织，都依据其在 Godot 中的运行效率、表现能力、开发体验和长期维护价值决定。不能仅因原样迁移更方便而延续不适合新平台的结构，也不为追求形式上的重构而改掉仍然合理的设计。

不强制维持一套完全脱离 Godot 的业务框架，也不把所有对象机械地扩展成庞大节点树。选择实现层级时，兼顾编辑器可操作性、运行频率、对象数量和维护成本。

一项运行状态保留一个权威来源。通知、表现与规则结算之间保持清楚的关系，避免依赖隐含的信号连接顺序维持玩法正确性。架构以减少真实复杂性为目标，不为尚未出现的需求提前建设通用实体框架、双语言后端或大型事件总线。

### 以工程判断推进决策

总体架构和技术路线依据当前代码、游戏需求、Godot 的能力，以及工程知识、经验和专业直觉直接作出判断。能够从原理和现有规模判断的事项，不以先建立对照原型、开展基准测试或完成大规模验证作为前置条件，也不先完整迁移明显不合适的实现再推翻重做。

时间和 Token 优先用于形成合理设计并推进实际重构，不为穷尽备选方案或消除所有不确定性反复验证。对尚有不确定性的判断，明确依据与取舍，保留局部调整空间；不把预测写成已经获得的实测结论。实现中的必要检查服务于具体改动或已经出现的问题，不扩张成独立的大规模测试工程。

### C# 是局部能力，不是第二套并行业务体系

只有当明确的计算需求、依赖需求或类型约束收益足以覆盖跨语言成本时，才引入 C#。需求与收益可以依据代码分析和工程判断识别，不以性能实测作为唯一依据，也不为了预防假想瓶颈而提前混写。扩展优先落在职责独立、输入输出清楚的边界上，而不是把同一条复杂玩法规则拆散到两种语言中。

跨语言接口保持少量、稳定、粗粒度；数据所有权留在执行主要工作的那一侧。避免逐对象、逐属性反复跨语言调用，也避免为了调用一次服务而复制整个世界状态。

两种语言可以互相调用，但不能跨语言继承，跨语言调用也不会自动拥有端到端的静态类型检查。因此采用组合与封装，而不是构造跨语言继承体系。[^2]

C++、Rust、GDExtension 与自定义引擎构建不进入默认技术栈。只有出现标准引擎与现有语言路径确实难以解决的需求，再单独评估。

## 三、运行架构与时间系统方向

按照成熟的 Godot 游戏工程方式组织运行时，将计算、渲染、输入、资源和生命周期纳入一致的设计。高效运行是合理组织工作的结果，不依赖机械换语言或不断削减内容。优先减少重复工作、无效遍历、频繁分配、不必要的引擎调用和无收益的表现叠加；可由引擎或 GPU 高效承担的工作，优先使用对应能力。

充分考虑桌面原生平台的并行处理和硬件利用空间。并行工作按任务职责、数据关系和引擎线程约束安排，不因旧 Web 实现的限制而回避，也不把所有逻辑多线程化当成固定目标。

采用固定战斗更新与渲染解耦的方向，优先利用 Godot 常规物理步、插值、暂停与时间缩放设施，不复刻浏览器循环和自定义子步组织。高刷新率显示不应强迫所有业务逻辑按同等频率执行。Godot 的物理插值支持固定更新与可变渲染之间的平滑显示。[^4]

操作响应、命中停顿、慢动作、运动曲线和防御窗口可以按原生环境重新调校，服务于已经确定的战斗方式和反馈方向，不追求旧参数、逐帧位置或随机轨迹的一致。游戏规则、视觉反馈和界面交互各自使用适合的时间语义，避免相互牵连。

设计时兼顾帧时间稳定、输入响应、瞬时计算峰值、资源占用和长时间运行行为，而不是只追求一个平均帧率数字。实际开发中出现具体问题时，可以利用已有日志和分析能力定位原因，避免将所有问题都归因于 GDScript；这些能力不构成启动重构或选定架构之前必须完成的专项工作。Godot 内置 Profiler 可提供脚本与引擎相关的时间信息；需要分析 C# 热点时，再配套使用托管代码分析工具。[^5]

## 四、渲染、画质与分辨率

### 高质量二维表现，以 Forward+ 为默认路线

采用 Godot 2D 与 Forward+，以 HDR 2D 支持更丰富的亮度层次、辉光和材质表现。选择 Forward+ 是为了保留高质量表现的技术空间，不是认定它对所有二维场景都更快；官方明确区分了各渲染器的基础成本与适用能力。[^6][^7]

视觉设计围绕游戏辨识度、层次和反馈服务，不为了使用高级功能引入无必要的三维复杂度。具体特效可以重新选择适合 Godot 的实现，不追求与旧版着色器或粒子参数等价。

### 画质等级改变表现成本，不改变游戏规则

先建立完整、协调的高质量视觉基准，再围绕同一套美术方向提供高、中、低等真正具有成本差异的画质等级。主要调整装饰密度、尾迹细节、灯光、后处理和复杂效果的表现成本，使不同设备能够选择合适的表现强度，同时保持技能辨识与关键战斗信息。

画质档不改变有效攻击数量、命中判定、战斗速度或规则更新频率。减少动态效果作为独立的体验选项，不简单等同于低画质。

默认在同一主渲染器内实现分级，不预先维护多套渲染器与多套特效实现。若明确需要覆盖主路线不支持的硬件，再评估额外渲染器；渲染器切换具有实际的视觉和功能差异，不能当成普通画质开关。[^6]

### 统一分辨率，按特效影响范围分层

以 1920×1080 为统一设计基准，提供可调整的游戏分辨率、窗口与全屏模式，并支持常见桌面宽高比和合理的界面缩放。设计基准是制作与布局参照，不是永远固定的实际输出像素数。Godot 区分设计尺寸、窗口与视口伸缩，项目需要在统一策略下管理这些关系。[^8]

世界、HUD 和文字使用统一的游戏分辨率策略，不沿用浏览器时期为开发方便设置的多套独立分辨率标准。分层用于决定哪些内容受到空间扭曲、辉光、模糊或震动影响，而不是建立“世界低分辨率、文字高分辨率”的两套长期显示体系。

重要文字和精确危险提示保持可读、位置明确；界面缩放不等于单独设置界面渲染分辨率。窗口变化与宽高比适配也不应意外改变战斗规则。

## 五、玩法、UI、声音、内容与数据

### 延续游戏设计，开放实现与调校

重构延续已经讨论确定的游戏定位、战斗方式、法书差异、遗物构筑与培养成长方向。打字驱动战斗、键盘为主的交互、施法与防御之间的关系，以及不同构筑形成的玩法差异，仍属于同一套游戏设计，不因更换引擎而被任意替换。

延续的是核心关系与体验方向，不是逐项冻结现有实现。具体数值、节奏、动作曲线、表现方式与内容组织可以依据原生平台重新设计；这些调整服务于既定玩法，而不是借技术重构重新定义另一款游戏。已有讨论继续作为设计依据，旧代码不再作为实现方式的上限。

### UI 外观延续，实现方式原生化

UI 是需要优先延续视觉设计的部分。保留现有字体风格、字号层次、色彩、留白、局部刻线、信息布局和开放式界面气质；通过 Godot 原生界面体系重新实现，而不是直接套用默认控件外观。

UI 视觉规范与参考画面成为共享依据，供开发者和 Agent 一致使用。尺寸适配、动画与交互可以改进，但不能因引擎更换或工具默认行为，未经设计决定就改变整体视觉身份。

外观以实际呈现为准，而不是以参数相同为准。尤其 HDR 2D 的线性色彩混合会影响半透明元素和字体边缘观感，旧参数不能直接代表相同视觉结果。[^7]

### 声音按原生游戏重新组织

使用 Godot 原生音频体系组织声音，以音频总线管理混音与效果。已有素材按效果需要复用，混音、方向感、并发、动态音乐和反馈节奏允许重新设计。[^20]

目标是清晰、有层次、可辨识的游戏音频，而不是完整复刻原有听感、浏览器音频接口、旧 HRTF 行为或声源参数。优先发挥 Godot 原生音频能力，按明确需求选择成熟生态工具；既不因旧实现限制表现，也不预先引入没有实际收益的额外中间件。

### 内容与用户数据保持单一来源

可编辑的游戏内容优先采用 Godot 资源与场景组织；外部交换、词库导入和用户数据选择适合的文件格式。Godot 自定义资源支持序列化和编辑器集成，适合作为内容创作的基础。[^9]

同一份权威数据不在多个格式中分别手工维护。需要不同产物时采用生成或导入关系，并保留稳定内容标识与数据版本意识。

现有图片、字体、音频和内容可以复用；原始资产、导入产物与用户数据分开管理。用户记录的延续按实际产品需求安排，不因迁移引擎自动扩张为完整录像、任意时刻续玩或云同步工程。

## 六、Vibe Coding 工具链选择

**默认组合：Windows 本地 Codex + Godot 官方 CLI + tugcantopaloglu/godot-mcp + 项目级 Skills。**

四者分别负责代码工作、引擎执行、运行时观察与操作、项目知识。MCP 不替代命令行，Skill 不替代执行工具，Agent 也不以盲目点击编辑器代替能够明确完成的结构化操作。

### 主 Agent：继续使用本地 Codex

以 Codex CLI 作为执行基础，IDE 扩展或桌面界面可以作为同一工作流的交互入口，不要求为了 Godot 更换主 Agent。优先使用 Windows 原生环境，使代码、编辑器、图形运行实例和工具进程处于容易识别的本地环境。Codex 官方支持 Windows 原生 CLI 与相关入口，不要求必须使用 WSL。[^10]

不把“本地开发”理解为“模型一定离线运行”。这里要求代码操作和 Godot 工具在本机完成；模型服务的连接方式另行遵循所选 Agent 的配置。

云端 Agent 可用于独立代码工作，但不作为本地 Godot 编辑器与真实图形状态的默认操作者。已有 Claude Code 等工具也可以作为替代入口，但项目架构不依赖某一家 Agent 的专有交互方式。

### 基础执行层：Godot 官方 CLI

Godot 官方 CLI 是启动、资源导入、项目运行和导出的基础入口。能通过文件编辑和官方命令清楚完成的工作，直接使用这些能力，不为每项操作增加 MCP 包装。官方 CLI 支持无界面执行、资源导入、场景运行及导出等能力。[^11]

当项目引入 C# 后，再把 dotnet 构建接入日常工作流；没有 C# 业务或插件编译需求时，不添加无意义的固定构建步骤。

第三方 CLI 可以减少重复操作，但应保持为可替换的便利层。游戏不能因为某个 MCP 或第三方 CLI 停止维护，就失去直接使用 Godot 开发和发布的能力。

### 主 MCP：tugcantopaloglu/godot-mcp

选择它作为当前主 MCP，依据是与 GDScript 主体、本地 Godot 工作流的匹配度，而不是工具数量或 Star 数量。

它采用本地 Node.js MCP 服务，无界面 Godot 进程负责项目操作，运行时桥接负责与游戏通信；工具涵盖 GDScript 检查、场景与资源操作、运行时树和属性、输入、截图、错误日志及基础性能监视。[^12]

其源码包含 Windows 路径处理，并通过本机 TCP 与游戏通信；截图处理会返回 MCP 图像内容，而不只是文字路径，适合支持图像输入的 Agent 观察画面。这里是文档与源码层面的选型依据，不代表已经在目标 Windows 环境完成实际接入。[^13]

必须明确它的能力边界：它不是对当前编辑器所有未保存状态的完整控制接口。磁盘中的场景、编辑器中的未保存修改和正在运行的实例，需要由开发流程区分；不能因为 MCP 能改场景文件，就认为它知道编辑器里发生的一切。[^12]

日常只开放需要的工具范围，以项目状态、运行控制、截图、日志和必要的场景操作为主。Codex 提供工具允许列表和禁用列表，可减少不相关能力的干扰。[^14]

运行时注入与调试桥接只属于开发环境，不成为正式发行物的运行依赖。涉及源码的编辑仍以可审查的文件变更为准；运行时属性调整用于观察和调优，最终需要明确保存到工程。

### Skills：项目规则为主，第三方知识为辅

建立少量职责清楚的 Skills：Godot/GDScript 开发知识、着色器与视觉知识、项目工具使用约定。具体目录和加载方式遵循所选 Agent 的现行规范；Codex 支持仓库内的 .agents/skills，并按需读取完整 Skill 内容。[^15]

fetasty/godot-skills 可以作为知识素材来源，优先参考 godot、godot-gdscript、godot-shader 三类。该库明确面向 Godot 4.6，不能直接作为其他版本的完整权威指南，也不将其中所有架构偏好原样升级为项目规则。[^16]

正式依据依次是项目的明确技术决策、锁定版本的引擎实际能力与官方文档、经筛选的第三方知识。遇到冲突应查清原因，不凭 Skill 或模型记忆臆造 API。

项目级 AGENTS.md 用作规则入口，指向本方案、视觉规范与必要文档；Skills 负责可复用的工作方法。避免把同一组长期规则复制成多份提示词，导致后续更新不一致。[^17]

### 其他候选的定位

**aigengame/godot-agent（gda）暂不进入默认组合。** 它提供 CLI、Skill 和 MCP，设计方向适合 Agent 自动化，但当前 Live 模式只支持 macOS/Linux；Windows 保留无界面操作范围，不能承担本方案需要的完整本地运行时工作流。[^18]

**LuoxuanLove/godot-dotnet-mcp 保留为编辑器上下文需求增强时的替代候选。** 它在 Godot .NET 编辑器内提供当前场景、选择状态、检查器与运行上下文。只有实际需要这类编辑器原生能力时才考虑替换主 MCP，不因为使用了 .NET 编辑器就必须安装它。[^19]

默认只保留一个主 Godot MCP。工具替换不改变主语言，也不为满足工具偏好而反向修改游戏架构。

## 七、Agent 协作与工程组织

### 让状态与修改结果可追踪

代码、资源、场景和长期配置进入版本管理。编辑器未保存状态与运行时临时修改不作为唯一事实来源。Agent 必须能够区分“运行时已改变”和“工程文件已保存”，避免产生看似完成、重启后消失的结果。

编辑项目优先使用结构化文件修改和合适的引擎操作，不把批量文本替换或反复模拟鼠标点击作为默认手段。场景与资源保持正常的 Godot 工程形态，使开发者能够接手，也使其他 Agent 能够理解。

### 控制并发写入与上下文范围

一个具体编辑器和游戏运行会话，默认由一个 Agent 负责写入和调度。需要并行时，按照清楚的任务和文件范围分工，不让多个 Agent 同时争用同一场景、运行实例和全局配置。

模型能力优先匹配任务难度：架构变化和复杂规则交给推理能力更强的配置，边界明确的局部编辑使用成本更合适的配置。上下文先聚焦相关代码、规则与当前错误，再按需要扩展，不把整个工程、所有日志和全屏截图重复送入每轮任务。

### 工具观察保持针对性

文本与结构化状态用于理解规则和对象关系，截图用于理解真实视觉，日志与性能信息用于定位具体问题。三者互补，不以截图替代所有结构检查，也不以没有错误日志推断画面正确。

Agent 根据当前代码与工程知识作出合理选择并持续推进，不先铺开大量比较原型、性能基准或重复测试来证明每项技术决策。时间与 Token 主要用于实现目标；必要观察和检查围绕具体改动与实际问题展开，优先利用已有入口，不临时建设庞大的验证脚本体系。

工具用于帮助理解工程、编辑内容和定位问题，不让重构过程转为围绕工具、测试和报告自我运转的工作。对已有清楚结论的事项直接执行，对不确定处保留可调整的边界，而不是无限扩大验证范围。

### 开发依赖与发行依赖分离

Node.js、Python、MCP、Skills 和 Agent 可以属于开发环境，不因开发使用它们就进入玩家的运行依赖。保留有价值的素材与数据处理工具，不要求所有外围工具重写成 Godot 脚本。

第三方引擎插件、MCP 与 Skills 固定可追踪的版本或提交，并按需要更新。选库关注真实能力、兼容范围、文档、维护状态和替换成本，不只看宣传功能数量。

## 八、决策边界与演进原则

可以直接作为长期基线执行的决策是：面向原生桌面、以 Godot 原生能力重构、.NET 版编辑器、类型化 GDScript 主体、Godot 2D、Forward+ 高质量路线、真实画质分级、统一分辨率、按特效范围分层、既定玩法与培养成长方向延续、UI 外观延续，以及本地 Agent 工具链。

留给后续实施按实际需要决定的事项，包括具体内容如何组织、哪些计算适合批处理、是否引入 C#、各画质档的参数、插件的具体接入方式和其他桌面平台支持。它们不是当前必须预先解决的问题。

技术演进以引擎知识、现有代码和工程判断为依据，优先选择在新平台上综合表现更好的组织方式，在收益明确时引入局部复杂性。性能、画面与维护能力的改善来自这些选择共同发挥作用，而不是让任何单一指标支配全部设计。既不为了保持旧实现而回避引擎优势，也不为了展示工程技巧或验证每项判断而增加无谓工作。

**最终形成的应当是同一款游戏在 Godot 原生平台上的成熟实现：玩法与视觉身份延续，架构、画面、运行效率和开发方式充分适配新环境；开发者和 Agent 围绕游戏本身工作，工具链提供帮助而不反过来支配项目。**
